## B14 — Real-DB self-report write path BLOCKED (schema/application mismatch)

Found this session while running the Postgres adapter against the real Supabase database.
Specific task: persisting a patient self-report (`dose_events`) on the real DB.
Root cause: `dose_events.confirmation_challenge_id` is NOT NULL, and the `core_guard_dose_event` trigger calls `core_consume_confirmation`, which requires a confirmed, unconsumed `record_self_report` challenge bound to the same regimen/occurrence/intake/idempotency. The application has no such step: `RecordSelfReportRequest.confirmed_challenge_id` is declared but never populated, no `record_self_report` challenge is ever issued, and the HTTP route passes none. The activation path DOES issue and consume a challenge correctly, so the gap is specific to self-report.
Why human/design decision is needed: the two resolutions are (a) wire the intended self-report confirmation flow (issue + consume a challenge) or (b) change the schema constraint — the latter is a safety-relevant decision and must not be done silently.
What was done instead of faking it: `PostgresDoseEventRepository._resolve_confirmed_challenge()` looks for a matching confirmed/unconsumed/unexpired `record_self_report` challenge and, if none exists, raises `ConfirmationRequiredError` — it refuses rather than manufacturing consent. The in-memory fake has no such constraint, so unit tests pass while the real DB blocks.
Resume at: `backend/app/infrastructure/postgres_repos.py` (`PostgresDoseEventRepository`) + `backend/app/application/dosing.py` (self-report path) + the `/doses/report` route; re-run `python scripts/db_integration.py`.
Impact: activation, dose-rule persistence, occurrence materialisation, due lookup, auth boundary and RLS isolation all PASS on the real DB; only the self-report write is blocked. This must be resolved before the Session 03 integration claim of an end-to-end real-DB dose flow.

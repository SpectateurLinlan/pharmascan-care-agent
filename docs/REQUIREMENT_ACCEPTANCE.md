# Requirement-Driven Acceptance

本规则是工程验收约束，不新增功能或审批权限。产品规范继续在 `MASTER_SPEC.md`，行为/证据索引在 [REQUIREMENTS.md](REQUIREMENTS.md)，暂缓/风险/审批在 [DEFERRED_WORK.md](DEFERRED_WORK.md)。旧 `BUILD_PLAN.md` / `status/tasks.json` 保留历史ID，不再用其旧快照推定当前完成率。

## 开始前

1. 阅读AGENTS与相关Deferred条目；找本轮有效原始要求、最新明确替代/否决与新增补充，识别existing code和已有直接证据，避免重复开发。
2. 区分owner批准、完成声明、建议、已替代、否决、未知来源。助手提出的方案不是owner需求；暂缓项“前置条件满足”不等于授权。原文不可访问写MISSING SOURCE，只问会改变结论的关键缺口。
3. 按独立可验收行为列轻量Acceptance Matrix，引用已有Requirement ID。小修在当前报告/答复内几行即可，不每次生成大型审计文档。尚无ID的新行为追加到所属领域，不重编号旧ID。
4. 说明组件ownership、公开DTO/API影响、依赖/迁移/安全风险、验收路径/环境和回退。既有未提交工作不清理、不覆盖；敏感写入/SQL/Auth/库存/审计/生产操作按具体授权执行。

## 最小Matrix

| Requirement ID / 原始来源与变化 | 具体预期与反例 | 代码/公开接口 | 直接验收与数据/版本/环境 | 实现 / 验收状态 | 生产/外部/真机 / 缺口与责任 |
|---|---|---|---|---|---|
| 引用已有ID或新增稳定ID | 触发→可观察行为；不能只写“历史聊天” | 路径/服务/API | 实际命令/用例/结果，或NOT RUN原因 | code存在≠PASS | 谁做什么，是否需批准 |

## 执行中

- owner中途追加要求：立即更新当前Matrix和验证路径；若改变范围/风险，说明边界，继续独立已授权工作。**完成后才新增的要求**作为新补充记录时间，不倒写成原任务当时已包含。
- 测试目标是行为：问题→tool选择/参数→真实记录/副作用→最终患者答案。Agent不以HTTP200/有回复/tool success算通过；数据库不以mock repository成功证明真实CHECK/RLS/事务；UI不以静态board或类型检查证明可用。
- 照片路由、识别准确性、授权、来源、普通消息保存、持久附件恢复分别验；thread身份/回看/恢复语境/草稿/历史侧栏分别验；Records布局/搜索/归组/计划/日期/排序/分页分别验。
- 只做必要定向测试；有明确旧证据且代码/环境无相关变化可复用，注明日期/版本/适用边界，不冒充本轮执行。不为填表重跑全部历史测试。
- 真实失败保留；不得跳过、改弱预期或硬编码数据制造PASS。截图条件必须一致；只用授权合成数据，scrub日志，不复制患者正文、JWT或私密图。

## 完成时

1. 逐项报PASS / PARTIAL / FAILED / NOT VERIFIED / BLOCKED / NOT IMPLEMENTED / SUPERSEDED。只给全局“测试通过”不算交付。非PASS写原因、影响、下一步责任/许可；代码存在和运行/验收/部署分层。
2. 证据注明代码/HEAD或working-tree基线、时间、命令/测试、输入规模/语言/时区、mock/DEMO内存/真实SQL/provider/生产/设备边界。保存失败原因与修复后证据，避免重复累计同一测试数。
3. 新截图/实际使用推翻旧PASS时标EVIDENCE CONFLICT；先核版本差异、测试缺口、范围改变或回归。不凭代码推现在生产状态，也不凭来源缺失认未实现。
4. 更新现有Requirement与Deferred交叉引用，仅依具体证据；保留ID、历史背景、风险、审批门槛。不要复制新Phase或把同一BUG拆成多份开发Task。
5. 报实际修改/遗留、Git status/diff、实际测试和建议提交范围；未经本轮具体批准不Stage/Commit/Deploy/生产写。已批准功能尚未全部满足时不能笼统宣称“本轮全部完成”。

PASS的最小语义：**特定版本、特定环境中，实际执行结果符合该条预期。** 本地PASS与生产未验可以同时成立。BLOCKED不是可忽略；已被明确排除/替代的行为不再算未完成。

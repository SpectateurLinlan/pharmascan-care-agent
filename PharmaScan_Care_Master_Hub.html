PHASE A

处方、药房标签与疗程管理

PDF/药袋/OCR/手动→核对产品规格剂型→有来源的计划及历史版本；缺失时留 Draft，提示补充资料，潜在相互作用只做提示。

PHASE B

Personal Gallery 准备

美国目录候选图不等于身份核验；患者裸片参考生成同模型版本向量，包装和铝塑板图片另存；不强制为建档拆药片。

PHASE C

Daily Smart Check（默认可不拍照）

正常快速自述 Taken/Not now/Unsure；需要时拍裸药片/包装→选择视觉/OCR工具→基于证据处理失败→两条状态独立记录视觉匹配与服药自述。

PHASE D

长期追踪、疗程更新与复诊准备

停药保留历史而非删除图库；追踪不确定剂次、症状/测量值、用户既有筛查/随访计划，生成药剂师讨论摘要；不代替真实医生。

二、产品定位与需求

Challenge 2： 长期自我健康管理而非急诊分诊。主用户是居家独立管理多种药物的成年人，特别优化中老年视觉/操作能力；不限于必须患有某一个疾病。任何 Patient 使用同一套页面。Caregiver 作为由患者授权且完成验证的通知联系人，当前不做第二套 Portal；Doctor / Pharmacist 为外部真实专业角色，MVP 不接医疗机构数据源、不做 Doctor Portal。患者可上传来源文件；模拟医生系统只是说明未来可互操作，不是真连接。

商业假设： 初期患者直接访问（B2C-ready），未来可探索社区药房、居家护理 B2B2C 分发或付费；没有验证过真实支付意愿，不要捏造 ROI、节省成本或减少临床错误率。

合规： 所有测试患者信息都是合成；不收集 NRIC；Singpass/NEHR 灰色 future only，不要实际接入；药片图像只输出可能的视觉匹配，不允许主动更改处方/补服/停药、不能证明实际吞服。实际新加坡商业医疗部署需 HSA 医疗软件分类与临床验证，不能凭“辅助”措辞直接断言不受监管。

三、从 Claude 完整用药生命周期吸收什么？

Phase A · 用药计划创建/变更： 药房药袋标签、处方 PDF、有字包装、用户手工录入、仅 Demo 可选的模拟医嘱来源 → OCR/结构化提取 → 精确的药品身份（成分、品牌、强度、剂型、IR/XR、市场） → 当前/历史处方查重 → 不全的用法提示补充 → 用户对照来源核对 → 新 Regimen 版本 → 确定性计划规则及带覆盖率的潜在 DDI/重复成分提示。药量不会自动从包装盒剩余数量推断疗程期限。

Phase B · 个人视觉图库： catalogue_seeded_candidate 可以在准确匹配到美国产品并允许使用目录图时先提供视觉候选图，但它不是已核实患者药品的 ground truth。病人自己的裸片照片按 3–5 张/面作为建议，不强制为建档拆药，得到 Stage2 256-d Embedding；药盒、药房标签、铝塑板/无字 blister 作为独立参考图片存储，不能与裸片 embedding 混合做余弦匹配。图库跨历史用药保留，但只有 Active Regimen 参考可用于当前剂次核对。模型权重/预处理升级后旧向量需版本检查/重编码。

Phase C · Daily Dose： 默认 Smart Check（稳定日常可一键自述吃药；新药、外观改变或不确定再建议拍照），另可选 Always Suggest、Reminders Only。每个剂次有 [Taken] [Check pill] [Not now] [Unsure]。有照片时分模态：裸片→质控/裁剪→个人 Gallery Match→不确定则 US C3PI Catalogue 搜索；有文字包装→OCR；无字透明或不透明 blister→查药盒/药袋/医嘱，不强迫拆药。图像相似度与临床身份分离、视觉记录与病人声称已吃分离。正常结果简短，不每次让用户重复看标签；异常只能解释有依据的照片原因（blur/反光/太小/重复框等），没证据不能让 LLM 乱猜。现有 /scan 已出现单颗药被框成两颗，未修复不能以此自动核对药量。

Phase D · 长期管理/疗程变更： 停药→结束当前 version、保留历史；再次开药→新 version。定时任务及患者聊天触发 Agent，读取自述服药、未报告和 unsure 的真实区别；询问困难/症状；记录血压血糖、睡眠或症状的时间数据；按用户原有计划安排随访/筛查/预防生活事项；最后生成药剂师或医生讨论清单。不可假装医生已经收到报告。

四、为什么是 Agent，而不是四阶段 Pipeline？

真正的 Agent 流程：Observe（对话/上传/提醒）→ Authorize & Retrieve Context（当前用药和历史）→ Plan（选择合适 Tool 或追问）→ Execute（OCR / Gallery / Catalogue / Regimen / Knowledge 等）→ Deterministic Safety Gate（证据、身份、计划、权限）→ Adapt/Abstain 或 Confirm/Act → Persist State / Follow-up。固定 Stage1 Detect → Stage2 Match → Stage3 Check → Stage4 Speak 可以作为“拍裸片”子流程；不是每个患者问题都必须走这条路径。比如“忘记吃没吃药”先查历史；上传有字包装优先 OCR；导入新药走 Enrollment；复诊总结走历史/健康任务工具。

应实际展示：用户说不清任务 → Agent 澄清；照片重复检测 → 独立规则拒绝把两框当成两颗；未知药 → 询问来源/另一角度，不强行配对；疗程更新 → 旧版本保留；跨会话重新登录 → Agent 能接着完成上次待处理任务。日志必须来自真实工具调用，而不是写死的四段对话。

六、部署与组件责任

  • UI：React + TypeScript mobile-first PWA；竖屏设计为主，横屏/桌面兼容，Voice-first + Text fallback。评委入口 Try Demo 用独立匿名 Auth + 各自的预设合成药单和七日历史，不能公用一个可随意修改的账号。
  • 主后端：Python FastAPI，Auth Gate、Application Services、状态化 Agent Orchestrator/ToolRegistry、确定性 Safety Gate、Vision/OCR/Knowledge Adapters、提醒/日志、typed DTO 和可测试依赖注入。
  • DB/Auth/Storage：Supabase PostgreSQL + pgvector + Auth + Private Storage，Patient/MedicationProduct/RegimenVersion/DoseEvent/GalleryReference/Embedding/Observations/CareTasks/AgentSessions/ToolCalls 分表，user RLS；不会把患者 DB 放到 HF Space。
  • Stage2：由队友维护 HF API /embed,/match,/identify,/scan；请求响应/模型版本/向量空间必须确认。建议新增 /model-info，检测/质控接口需协商；不要要求你这边直接重训模型。
